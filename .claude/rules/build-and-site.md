# The site, the catalogue, the help pages and publishing

Loaded when a session works on the build tools, the site or the workflows. Moved word for word from `CLAUDE.md` (12 October 2026); keep it in step with the code, as `CLAUDE.md` asks.

## How the code is built (the site)

- **The installable web app (PWA) is built from the same `src/`** into `site/` by `npm run build` — not committed (Git ignores it); `npm run serve` shows it at `http://localhost:8080/`. It adds what a single file can't carry: `src/site/` (web app manifest, icons, the service worker `sw.js`, whose version the build fills in from a hash of the site's files). fmIDE's page gets the manifest links through its `<!-- build:site-head -->` marker, which is empty in `apps/`. The service worker keeps only the site's own files (offline) and never contacts another site. See `docs/step5-publish.md`.
- **The library's catalogue** (step 8c-3, `tools/build-library.js`): the community library repository `taroyamakatrmttm-star/fmide-library` (public) is a git submodule at `library/`, pinned to one commit (a pull request's preview builds from it). The live site builds from the library's latest `main` instead, so a pack merged there is published by itself: the deploy job runs on every merge into fmIDE's `main`, every hour (`schedule`; it publishes only when the library's `index.json` differs from the live site's) and on Run workflow (`workflow_dispatch`); if the latest library fails fmIDE's checks, it builds from the pinned commit and the run ends in an error. Moving the pointer is only needed for previews. When `library/` holds anything, `npm run build` checks it with the library checker (a failure stops the build, nothing written) and writes `/library` into the site: plain HTML with no JavaScript (every pack text through `escapeXml`, links only from pack ids), the pack files byte for byte, `index.json` (kind `fmIDE-library-index`; an item carrying an fmGraph board is marked `board: true`, G5c), under its own policy (`default-src 'none'`, styles from the site; pack files download). It is added after the app's version and offline list are worked out, and its `_headers` rules are always there, so a new pack never changes the app's version. Without `library/` (or empty) there is simply no catalogue; the deploy uses `--require-library`. Tests never use the submodule: they pass sample libraries.
- **The help pages** (step 10 H4a, `tools/build-help.js`): every site build writes `/help` from the apps' help text — fmIDE's topics (`/help/<id>`), tutorials (`/help/tutorials/<id>`), every topic on one page (`/help/all`), What's new (`/help/whats-new/`, a page per update, `/help/whats-new/<id>`; H5c), and ExcelExporter's (`/help/excel/…` and `/help/excel/whats-new/`, under its own licence). Plain HTML with no JavaScript, every text through `escapeXml`, links only from ids (letters, digits and dashes, not a name the pages use); `{cmd:id}` shows the command's icon, name and first ribbon tab, read from fmIDE's source (the `COMMANDS` list's one-line entries and `DEFAULT_RIBBON`; test group 34 compares them with the app — keep those entries in their form). A topic, tutorial or update naming a missing command or topic, or an update with a bad id or a date out of order, stops the build (`HelpError`, nothing written). Its own policy (as the catalogue's, `HELP_POLICY`); added after the version and offline list, like the catalogue; styled by `src/library/style.css` plus `src/help-pages/help.css`.
- **Publishing** (`docs/step5-publish.md`): after the tests pass — on GitHub in 4 parts at once (the job `test-part`; `tools/test-parts.js` puts every test file in exactly one part, spread by the measured times in `tests/test-durations.json` — refresh them with `node tools/test-parts.js --measure LOG` from a run's log when the parts drift; every test on every change; the check `test` green only when all 4 passed), once per pull request and on `main` after a merge — the `deploy` job in `.github/workflows/tests.yml` uploads the site to Cloudflare Pages — a merge into `main` updates the live site, a pull request gets a preview address posted on it. The build also writes `site/_headers`: a strict security policy that lets each page run only its own inline scripts (by hash) and connect only to the site itself. **Never add anything that loads or sends to another site** — the policy blocks it by design (fmIDE's `connect-src 'self'` is what lets Browse Library read `/library`, and nothing else). `tools/pages-server.js` serves the site locally the way Cloudflare does (short page addresses, folder addresses like `/library/`, `_headers`); `npm run serve` and the tests use it.
